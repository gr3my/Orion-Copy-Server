# Ports

Every port the backend listens on, what it is for, and whether it may face the internet.

Defaults below are the `.env` defaults (`ORION_BACKEND_PORT_*`, `ORION_GAME_UDP_*`).
Client-facing services (Mothership, StationDb, EOS, EOS-WS) listen on
`ORION_PUBLIC_BIND`; management services (dashboard, orchestrator) always stay
on `ORION_INTERNAL_BIND`. Both default to loopback; a reverse proxy (Caddy, see
`deploy/Caddyfile.example`) or tunnel on the same host fronts the public ones
on 443. Set `ORION_PUBLIC_BIND=0.0.0.0` only when remote hosts must reach the
backend directly (split deployments, raw-IP mode) — `install.sh` /
`install.ps1` do this automatically when no domain/tunnel is set — and firewall
accordingly. (`ORION_HTTP_BIND` remains as a legacy single-knob fallback.)

## Backend services (TCP)

| Port | Service | Who talks to it | Public? |
|------|---------|-----------------|---------|
| `90` | Mothership — player login/auth + player data | Game clients (`BaseUrl`) | **Via reverse proxy only** (or public bind in raw-IP mode) |
| `78` | StationDb — stations, roles, deployments, server registration | Game servers (`register_server`, heartbeats, config fetch); dashboard proxy | **No by default** — open only via `ORION_EXPOSE_STATIONDB=1` (+ `ORION_STATIONDB_CIDR`) |

### StationDb public vs server routes (`orion.<domain>` → `:78`)

The public reverse-proxy host serves **game/client traffic only**. Server-control
writes are blocked there by the Caddy template (`deploy/Caddyfile.example`,
also generated by `install.sh`) and stay reachable only directly
(firewall-scoped `:78`) or on a private host:

| Route | Public via Caddy? | Notes |
|---|---|---|
| `GET /stations`, `/stations/{id}`, `/v1/stations*`, `/v2/*` reads | ✅ proxied | browser reads, deployment-config fetch |
| `POST /users/log_in*`, `/v2/users/log_in` | ✅ proxied | client + quest-fetch logins |
| `GET /v1/deployments/{id}?include_station_config=true` | ✅ proxied | game-server config fetch |
| `POST /register_server` | ❌ blocked (404) | creates stations/sessions; direct `:78` only |
| `POST /server_heartbeat`, `POST /update_player_count` | ❌ blocked (404) | watchdog/count feeds; direct `:78` only |
| `POST /stations/create` | ❌ blocked (404) | station creation; use `/game` proxy or direct |
| `/v1/server/admin/*`, `POST /v1/board/upload` | ❌ blocked (404) | destructive/writes; key-gated + private |

Do NOT remove these blocks without enabling `ORION_REQUIRE_REGISTRATION_KEY=1`
(after confirming your payloads send `x-server-api-key` on those routes).
Key-gated mutations (roles, config, bans) remain reachable but require a valid
credential either way.

### How StationDb tells public traffic from local traffic

Caddy dials StationDb over loopback, which would otherwise look "internal" to
`StationApiGuard` (and mutations would go unauthenticated). The Caddy template
therefore stamps public traffic with `X-Orion-Public-Proxy: 1`, and the guard
ALWAYS treats a marked request as external:

- direct loopback, no marker → internal (game servers, local tooling)
- loopback + marker → **external** (public Caddy traffic — needs the admin key
  for non-open writes)
- remote address (± marker) → **external** (the marker grants nothing extra)

The marker is only honored on loopback sockets with the exact value `1`
(`header_up` overwrites any client-sent value), and forwarding headers
(`X-Forwarded-For` etc.) can never make a request internal. Unit tests cover
all cases (`backend/tests/OrionCopyServer.Tests`).
| `50` | EOS gateway — server list / matchmaking (`/matchmaking/.../filter`, `/sdk/...`) | Game clients (via hook/redirect) | **Via reverse proxy only** (or public bind in raw-IP mode) |
| `80` | EOS websocket — lobby / RTC / notifications | Game clients | **Via reverse proxy only** (or public bind in raw-IP mode) |
| `8080` | Dashboard API + basic UI (`/api/*`, `/auth/*`) | Operators (browser, scripts) | **No** — SSH/RDP tunnel only, never opened by installers |
| `3000` | Next.js dashboard UI (optional) | Operators (browser) | **No** — binds `127.0.0.1`, tunnel only |
| `9095` | Orchestrator control (HalcyonSocket HTTP) | Localhost / trusted tooling | **Never** — internal bind + loopback-or-key mutations |
| `9100` | Orchestrator agent TCP (allocator agents) | Your own game-server hosts | **Never public** — `ORION_AGENT_KEY` auth + `ORION_AGENT_BIND` (loopback default) |

## Game traffic (UDP)

| Port | Purpose | Public? |
|------|---------|---------|
| `7777–7787` | UE game traffic, one port per server instance (7777, 7778, …) | **Yes — the game itself. UDP, not TCP.** |

## Rules of thumb

- If only TCP is open, players authenticate fine and then can't join anything.
  The miss is almost always `7777–7787/udp`.
- With a domain/TLS, service ports (`90/78/50/80/8080/9095/9100`) stay on loopback
  and the reverse proxy is the only public ingress (443/tcp, plus 80/tcp for
  certificate issuance). Without a domain they are plain HTTP; `install.sh`
  binds publicly in that mode — restrict them to your own hosts.
- `:78` has an open `POST /register_server` by design (servers self-register),
  so anyone who can reach it can list ghost stations in your browser. Keep it
  private — that is the actual access control for registration. The installers
  never open it unless `ORION_EXPOSE_STATIONDB=1`; optional
  `ORION_REQUIRE_REGISTRATION_KEY=1` adds a server-key check (enable only after
  confirming your payloads authenticate on that route).
- `:9095`/`:9100` must stay private. `:9100` agents authenticate with
  `ORION_AGENT_KEY` (loopback skips it) and unauthenticated peers are dropped
  before any message is honored — but the port itself must still never face the
  internet: bind `ORION_AGENT_BIND`, firewall to agent hosts.
- The dashboard (`:8080`, `:3000`) requires the admin key / session, but keep it
  unexposed anyway and reach it over `ssh -L 8080:127.0.0.1:8080 user@host`.

## Verify

Linux: `ss -lntup | grep -E ':(90|78|50|8080)\b'` and `ss -lnup | grep 7777`

Windows (elevated): `.\install.ps1 -Status`
